# Keep the generated prose in sync with the catalog

`docs/rules.md` is generated by `sf init` from the catalog, and then it is
meant to be hand-edited: the whole point of L4 is that a repository writes its
*own* reasoning for a rule rather than shipping the generic one forever.

That makes it a derived artifact that is also legitimately hand-edited, which
is precisely the case a hash lock cannot express. So nothing currently notices
when a rule's `why` or `fix` changes in the catalog and the document keeps
quoting the old text.

This was found the honest way: a `fix` line in `L3.GATE_HAS_FRESH_EVIDENCE`
named a command (`sf evidence record`) that never existed. The catalog was
corrected and `docs/rules.md` kept the dead reference, because
`L4.EVERY_RULE_HAS_A_WHY` only checks that a rule id is *cited*, not that what
surrounds the citation is still true.

Candidate shapes, none obviously right yet:

- record a digest of each rule's prose next to its citation, so the document
  fails when the rule's text moves and forces a human to re-read the section;
- split each section into a generated block and a hand-written block, and lock
  only the generated one;
- accept the drift for `why`/`fix` and check only that commands named in a
  rule's `fix` exist in the CLI — narrower, and it would have caught this one.

The third is the cheapest and catches the class of error that actually
occurred. Prefer it unless a second kind of drift shows up first.

**Exit condition:** a rule's `fix` naming a command that `sf` does not accept
fails `sf check`, proven by a mutation fixture that does exactly that.
